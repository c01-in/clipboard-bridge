# 0.2.0 preview — files alongside your clipboard

Status as of 21 October 2026 (America/Los_Angeles): Windows 0.2.0.0 is **in Microsoft Store certification**, configured to publish automatically after approval. It is not live yet. Android and Windows source/review versions are 0.2.0. The latest public GitHub release is still **0.1.4**; no new GitHub release or Google Play upload is implied by these notes.

## Clipboard or saved files

- Copy text or one image on Windows for automatic clipboard sending, or use the tray action / `Ctrl+Alt+V` manually.
- On Android, send clipboard text or one image from the foreground app. The dedicated image-to-clipboard system picker accepts exactly one image.
- Share one image through **Clipboard Bridge** to the computer clipboard. Shared plain text requires an explicit Send tap. The share entry follows the localized app name.
- Send multiple photos, videos, documents and other attachments through Android Share or **Send files…**. The app uses Android’s system picker, not a custom file browser. Even one image selected through Send files is saved as a file.
- Send files to Android through the Windows tray picker or native **Share → Clipboard Bridge** panel. The standalone desktop installer also offers classic **Send to → Clipboard Bridge**.

## Progress and storage

- Both endpoints show progress. Success requires the receiver to save the files and return an authenticated receipt.
- Windows defaults to Downloads. Set another destination in **Settings → Save received files to → Change folder…**, or open the receiving folder from the tray.
- Android 10+ defaults to **Downloads/Clipboard Bridge**; Android 8–9 require a selected receiving folder. No broad all-files access is requested.
- Original file bytes are preserved; existing destination files are not overwritten and received files are not opened automatically.
- The Windows sending window closes three seconds after success. Failures and cancellations remain visible.
- File batches allow 1–1,000 files and expire after one hour. The 16 MiB clipboard-content limit does not apply to file mode. Folders and automatic restoration of outgoing handles after a process restart are not supported.

## Windows Store edition

- Full MSIX for Windows 11 build 22000 or later, x64, including the signed Android companion APK.
- Per-user broker, login startup task and native Share target; no elevated Windows service or separate .NET installation.
- Tray, broker and CLI share one bundled .NET runtime. The package adds no Electron, WebView2 or Windows App SDK runtime.
- The Store edition has separate per-user encrypted state from the standalone service edition. Back up configuration and re-pair when changing editions; avoid running both brokers concurrently on the same port.
- Microsoft signs the Store package after certification. Existing GitHub EXE downloads remain unsigned.

## Still no account or Firebase setup

No app account, Firebase project, service-account key or maintainer relay is required. Google Play services and Google network access remain required; unsupported networks are not fixed by this release. Android needs no idle foreground service, but active file transfers use temporary foreground work and progress notifications. Windows tray pause stops automatic clipboard sending; Android pause rejects new sending and receiving while preserving pairing.

Both apps follow the system language, with nine supported locales and English fallback. Windows settings keep the receiving folder visible and the version at the bottom.

## Verification and remaining limits

The current preview has 112 Windows automated checks and 20 Android file-interoperability instrumentation tests, plus Android lint. The Store workflow additionally passed full MSIX validation, a real per-user broker and authenticated IPC check, one-runtime and privacy checks, complete companion APK download/hash verification, and real Store API authentication. See [file-transfer evidence](../file-transfers.md#verification) and [Store setup](../microsoft-store.md).

Emulator interoperability does not prove file wake-ups on every physical device. Store certification, Store-delivered installation/update, all vendors, prolonged sleep and every network configuration remain unverified. The previously reported second WeChat copy toast remains unattributed; these notes do not claim it is fixed.
